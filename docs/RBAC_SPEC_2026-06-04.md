## 2. Modell

### 2.1 Identität & Rollen-Quelle
- Login = bestehender **Discord-OAuth** (`web/auth.py`). Nach Login kennt das Dashboard
  die **Discord-User-ID** + dessen **Rollen-IDs** in der Haupt-Guild.
- **Mapping Discord-Rolle → Dashboard-Bereich/Recht** liegt in einer DB-Tabelle
  (im Dashboard pflegbar, Owner-only) — NICHT hardcoded, damit neue Rollen ohne Deploy gehen.

### 2.2 Ressourcen (Bereiche)
Discrete Bereiche, jeder an eine Discord-Rolle koppelbar:
- `minecraft` (BMC5 + Vanilla, oder getrennt `mc_bmc`/`mc_vanilla`)
- `satisfactory`
- `leveling` · `moderation` · `lfg` · `temp_voice`
- `admin_bot` (Modul-Verwaltung) · `system` (Service-Restart/Config) · `rbac` (Rollen-Mapping)

> **Offen (mit Marco):** MC als 1 Bereich oder BMC5/Vanilla getrennt? Welche der
> Community-Bereiche (leveling/moderation/lfg) brauchen eigene Rollen vs. fallen unter „admin"?

### 2.3 Aktionen
`view` (ansehen) · `edit` (Configs ändern) · `control` (Aktionen: Restart, Player-Ban, RCON).

### 2.4 Default-Regeln (aus B2)
- **Eingeloggt + keine spezielle Rolle = `member`** → `view` auf **alles**, `edit`/`control` auf **nichts**.
- **Bereichs-Rolle** (z.B. „minecraft") → `view`+`edit`(+`control`?) **nur** auf ihren Bereich,
  `view` auf den Rest (Member-Default). **Welche Aktion genau pro Rolle = B2-Matrix, offen.**
- **`owner` (Marco)** → alles (`view`+`edit`+`control` überall, inkl. `rbac`/`system`).

### 2.5 Permission-Auflösung
```
perms(user) = owner? ALLES
            : union( bereichs-rechte je Discord-Rolle des Users )
              ∪ member-default (view:*)
```
Effektives Recht für (Resource, Action) = ist es in der Vereinigung? → erlauben, sonst 403.

## 3. Enforcement (zweischichtig — Pflicht)

1. **Server-seitig (autoritativ):** FastAPI-Dependency `require_perm(resource, action)` an
   jeder Route. View-Routen → `view`, POST/Config → `edit`, Aktions-Routen (Restart/Ban) →
   `control`. **Nie nur UI-Hide** — server-seitig ist die echte Grenze.
2. **UI (Komfort):** Nav-Einträge + Buttons ausblenden was der User nicht darf
   (Template-Kontext bekommt `perms`). Verhindert tote Klicks, ist aber **kein** Schutz.

`web/auth.py` wächst von „ist in Whitelist? ja/nein" → `current_user` enthält
`{discord_id, roles[], perms}`. Neue Dependency-Factory `require_perm(...)`.

## 4. Audit-Log (B4)

- Neue Tabelle `dashboard_audit` (Migration vX): `id, ts, discord_id, username, resource,
  action, detail (JSON: was geändert, alt→neu), ip`.
- Jede **`edit`/`control`-Aktion** schreibt einen Eintrag (Config-Save, Restart, Ban, Rollen-Mapping-Änderung).
- Eigene Dashboard-Seite **`/audit`** (Owner-only): Tabelle, Filter nach User/Bereich/Zeit.
- PII-Hygiene: `discord_id` ok (DSGVO-Audit-Trail), keine Secrets im `detail`.

## 5. Rollen-Mapping-Verwaltung (im Dashboard, Owner-only)

- Seite **`/rbac`**: Liste „Discord-Rolle → Bereich(e) + erlaubte Aktionen".
- Marco wählt eine Discord-Rolle (Dropdown aus Guild-Rollen) + hakt Bereiche/Aktionen an.
- Schreibt Tabelle `rbac_role_map` (`role_id, resource, action`).
- **B3/B5:** Sobald Marco die Discord-Rolle einem User gibt, greift das Mapping automatisch
  (keine zusätzliche Dashboard-Zuweisung nötig).

## 6. Daten-Modell (Migration, additiv)

```sql
CREATE TABLE IF NOT EXISTS rbac_role_map (
  role_id   TEXT NOT NULL,   -- Discord-Rollen-ID
  resource  TEXT NOT NULL,   -- minecraft | satisfactory | leveling | ...
  action    TEXT NOT NULL,   -- view | edit | control
  PRIMARY KEY (role_id, resource, action)
);
CREATE TABLE IF NOT EXISTS dashboard_audit (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  ts        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  discord_id TEXT, username TEXT,
  resource  TEXT, action TEXT, detail TEXT, ip TEXT
);
CREATE INDEX IF NOT EXISTS idx_audit_ts ON dashboard_audit(ts);
```
Owner-ID bleibt ENV/Config (`MARCO_DISCORD_UID` o.ä.) — Owner ist nicht über die Map regelbar
(Selbst-Aussperr-Schutz).
